# Cursor implementation contract — FloqR photoreal jerseys

Implement this feature in the existing FloqR/ShoutOut application. First inspect its actual framework, template registry, editor input schema, preview/export pipeline, display player, queue, authorization, storage, and tests. Reuse those systems. Do not replace the application or create a parallel playback service. Report integration points from actual files. Continue with implementation after inspection. This package is an implementation brief and starter contract, not finished photoreal jersey assets or an audited repository patch.

## Product behavior
The customer supplies exactly three content inputs: Name, Number, and optional ShoutOut message. Team/edition comes from the selected template; it is not editable text. The first scene shows TWO photoreal views of the same customized jersey, matching the supplied visual: back on the left, front on the right, slightly overlapping, full shoulders and hems visible. The front is the foreground object. Name appears only on the rear nameplate; the same Number appears on front and rear. The fixed team wordmark stays on the front. Never put the customer's name where PHILA or MARYLAND belongs.

Scene 1 lasts exactly 7,000 ms. Scene 2 is a separate full-screen ShoutOut card lasting exactly 5,000 ms. Total is 12,000 ms. Treat “frame” here as a scene, not a single video frame. A hard cut is the default; no fades, white flashes, blank frames, or timing lost to transitions. Return control to the existing queue after one complete 12-second item. Loop only when the display player is explicitly in looping preview mode. No independent jersey rotation, extra back-view scene, or split of the seven seconds between front and back.

If the optional message is empty/whitespace, show only the jersey scene for seven seconds and then advance; never show an empty five-second card. Preview must explain this behavior. Freeze submitted content for the duration of the item. Handle live edits as a new preview, not partial edits during playback.

## Photorealism is a release requirement
Deliver high-resolution, reusable front/rear blank jersey assets or a verified 3D garment with realistic drape. Flat SVG shirt silhouettes, CSS polygons, generic sports shirt clipart, and baked photographs with someone else's number under a text overlay are unacceptable final output. Include knit/mesh structure, piping, seams, stitching, fabric weight, restrained wrinkles, natural edge thickness, and reference-consistent silhouette. Photograph-like does not mean faded: keep saturated team pigments, clean white cloth, deep blue/black lettering and crisp multicolor edges. Use neutral studio lighting. No vintage filter, desaturation, chalky haze, low-opacity whole-jersey overlays, excessive bloom, or clipped whites that erase fabric detail. Keep the jersey layer at opacity 1.

The tiny uploaded reference is a composition target, not an export master. Do not upscale it and call that photoreal HD. Build source garment textures at sufficient resolution for the largest requested master, then downsample only once with good filtering. Preserve alpha edges without white fringes. Validate on both light and dark QA backgrounds. Normal fabric shadows are expected; globally washed-out colors are not.

Preferred deterministic production pipeline:
1. Prepare true blank front/back garment plates from authorized high-resolution source material, preserving silhouette, trim, seams, lighting and drape. Remove old names/numbers completely with a reviewed clean plate; keep fixed wordmarks in their own accurately registered layer. Alternatively use a properly UV-mapped garment and pre-rendered camera views if the repository already supports this.
2. Store base albedo/photographic garment, alpha, fixed wordmark/patch artwork, name/number masks, garment-local coordinates, UV or displacement map, luminance/shadow map and highlight map separately. A 2D pipeline may precompute the maps offline. Use a named, documented coordinate system per front/back asset.
3. Render exact name/number glyphs from approved team-specific font assets or a verified glyph atlas; do not approximate the team wordmark with a generic font. Text and wordmarks must be deterministic, not generated by an image model. Verify source lettering, counters, stroke widths, outline/drop-shadow direction and curvature visually.
4. Warp dynamic artwork to the cloth surface; clip to the correct panel. Apply subtle cloth shading/texture to dynamic artwork so it appears printed/stitched into the jersey, without reducing pigment saturation globally. Match actual reference construction instead of adding exaggerated embroidery. Keep all lettering legible.
5. Composite both views with consistent lighting/perspective. Preserve fixed team marks exactly. Precompute/cache costly preparation; never call generative AI on every keystroke or at display playback. If AI is used offline for blank fabric cleanup, manually review edges and fixed trim/marks, then freeze/version the asset. Never ask an image model to spell customer text.

Use the existing rendering stack when it can meet these requirements. A canvas/WebGL compositor with precomputed garment maps is acceptable; a new full 3D dependency is optional, not mandatory. Keep browser preview and server export consistent through shared geometry, fonts and fixtures. Missing assets must produce an editor-facing preparation error and block publishing that template; never silently substitute a flat shirt or another team's assets.

## Input contract and fitting
Name: required, trimmed, NFC-normalized, 1–24 grapheme clusters as an initial product limit. Allow legitimate Unicode names, spaces, apostrophes, hyphens and periods. Uppercase only in rendered styling where the jersey reference calls for it; preserve original input for editing. Use grapheme-aware validation. Font coverage must be checked before confirmation; return a useful editor validation error for unsupported glyphs, never tofu blocks. Start with natural jersey nameplate size, tighten tracking slightly if needed, and reduce within a documented minimum. Never overflow onto collar, arm openings, or number. Preview the final fitting. Do not silently truncate or make a long name unreadably small.

Number: required STRING matching ^[0-9]{1,2}$, allowing 0, 00, 01, 7, 21 and 99. Do not coerce to integer or lose leading zeroes. Name customization has no relationship to a real player roster. Preserve front/back equality. Use different measured layouts for one and two digits while keeping visual weight and baseline consistent.

ShoutOut: optional, trimmed, NFC-normalized, maximum 160 grapheme clusters including spaces as an initial limit; support line breaks. Render as text, never HTML. Measure text using the final loaded font. Wrap only at valid boundaries, respect safe margins, limit line count (start at four), and enforce a legible minimum at native panel pixels. If it cannot fit, give a validation message to shorten it. No scrolling needed to read the whole message within five seconds, no ellipses or silent clipping. Use large, high-contrast text with a clean team-colored background. Support Unicode/emoji only where export and player fonts match. Show an editor-facing validation error for unsupported glyphs. Do not add customer-visible configuration fields for implementation internals.

Validate the same payload client and server. Use existing auth, venue/tenant permissions, moderation and content policies. Escape output; reject control characters except message newlines. Resolve selected template IDs on the server; do not accept arbitrary URLs, script, font paths or file paths from customers. Upload references only through existing authorized asset workflows.

## Playback, export and resilience
Preload/decode both jersey plates, fonts and the message scene before the queue item's clock starts. Reuse the display player's authoritative clock and completion callback. If none exists, derive the phase from elapsed monotonic time with requestAnimationFrame; do not chain 7s and 5s setTimeout calls. Handle background/resume consistently with existing player rules. Cancel stale renders and release GPU/image resources when unmounted. Do not let multiple timers fire completion twice. Keep native-resolution preview and exports aligned.

Support the existing player format first (scene JSON/HTML/canvas/video as applicable). If video export is supported, produce a 12-second constant-frame-rate MP4/WebM using a compatible codec, exact target pixel dimensions and correct aspect; at 30 fps scene 1 is frames 0–209, scene 2 frames 210–359. For the no-message case export 210 frames. GIF may be offered only as a secondary compatibility export: its limited palette can cause banding and color degradation, so it is not the master. If GIF is needed, use variable delays of exactly 700 and 500 centiseconds for the two static scenes, and verify a capable decoder; do not promise precision in every GIF viewer. Preserve sRGB for images and configure video conversion/color tagging consistently. Check color after decoding the final export; an untagged video conversion can look faded despite correct source colors. Never invent or overwrite device calibration; offer native-panel QA in the existing admin preview.

Persist selected team/edition, immutable template asset version, three input values, display preset and native pixels, scene durations, renderer version, output references and export job status using existing conventions. Scope cache keys to tenant where assets/content are private; include text, fonts, aspect/pixels and asset versions. Avoid cross-tenant content reuse. No external hotlinks during playback. Retain the old template behavior outside this feature.
